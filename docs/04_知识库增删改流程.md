# 04 · 知识库怎么增删改

这份讲清楚：知识从哪来、**新内容怎么进来**、**卡片能不能改**、增/删/改一条知识分别怎么做、冲突怎么处理。先讲概念，再讲流程，最后给跑流程的同事一个技术附注。

## 先分清两种角色

| 角色 | 做什么 | 在哪做 |
|---|---|---|
| **业务 / 审批人**（非技术） | 确认新主题、合并重复、裁决字段冲突 | 在**审批页**点页面 |
| **跑流程的同事**（技术） | 把新内容喂进去、重新生成知识库 | 跑几条命令（见文末附注） |

非技术使用者主要负责"审批/裁决"，"重新生成"由技术同事执行。

## 知识是怎么建出来的（一条流水线）

新内容从进来到能被问答，要走这几步（名字不用记，理解顺序就行）：

1. **接入（ingestion）**：把 Confluence 页面 / JSON 内容读进来。
2. **解析（map）**：把每页拆成小节、表格、要点。
3. **发现主题（discover）**：从里面找出"候选主题"，等人审批。
4. **审批冻结**：你在审批页确认主题（合并/新建/降级）——这是**防碎片化的人工闸**。
5. **生成卡片（reduce）**：按冻结好的主题，把原文提炼成一张张卡片。
6. **冲突复核**：同一字段出现多个值时，**大模型先复核给建议**，你在审批页**红色面板**里拍板（见下）。
7. **建检索库（load）**：把原文小段（chunk）和卡片存进可检索的库，问答就能用了。

> **chunk 是什么**：第 7 步会把每页切成很多"小段"（chunk）存进检索库，问问题时按相关度召回这些小段——这是 RAG 那条线的检索单位。卡片是另一条线（结构化词条）。两条线同一批原文、各建各的。

## 新来一份 Confluence / JSON 怎么接入

有两种入口，效果一样（都会走上面的流水线）：

- **真实 Confluence**：内网对接 Confluence，重新跑一遍流水线，新/改的页就进来了。
- **JSON 收件箱**：把新页写成 JSON 文件丢进 `inbox/` 收件箱（一份文件一页，或一个数组多页）。适合"内容还没进 Confluence、先手动喂一份"的情况。
  - 关键字段：每页至少要有标题和正文；**版本号/更新时间要填得比被替代的旧页新**，这样新值才会被当成"最新"，并触发冲突复核。

接进来后，**务必到审批页走第 4 步和第 6 步**（确认主题 + 裁决冲突），否则新内容可能碎片化、或带着未确认的冲突。

## 冲突是怎么处理的（重点）

同一个字段，不同页面/版本给了**不同的值**（比如门户链接旧页是 A、新页是 B），系统会：

1. **自动先取最新的值**，不卡住流程；
2. 把这条冲突**红色**列在审批页顶部的「字段冲突复核」里；
3. 让**大模型先复核**：建议用哪个值、为什么、风险高/中/低、置信度多少。

你要做的：在审批页点 **「采纳建议并冻结」** 或某个候选的 **「选这个」**。

- 你的决定会**写进一个"账本"**，**以后重新生成知识库也不会被覆盖掉**——这是它和"自动取最新"最大的区别：人拍过板的，就一直按你说的来。
- 如果之后又冒出**新的取值**，这条会重新变红提示"有新值"，请再确认一次（防止偷偷换了你没注意）。

## 卡片可以编辑吗？

**不能像改文档那样自由改卡片文字。** 卡片是机器从原文**自动生成的只读产物**，每个字都要能追回原文出处。这样设计是为了**不让任何人手塞进没有依据的内容**。

那要改卡片内容，怎么办？通过改它的"原料"：

| 你想做的 | 正确做法 |
|---|---|
| **改一条事实的值** | 改源页内容 → 重新生成；或者如果是"多值冲突"，在审批页冲突面板里**选定正确值**（冻结） |
| **改主题的名字/别名/范围/小节** | 在审批页编辑词表里那条主题，导出后重新生成 |
| **把两张重复卡合并 / 新建一张卡** | 在审批页做"合并 / 新建 / 降级"，重新生成 |
| **删掉一条知识** | 删源页（或从收件箱移除）→ 重新生成（会自动丢弃）；或在审批页把该主题 drop |
| **加一条新知识** | 走上面"新来一份 Confluence / JSON 怎么接入"的流程 |

一句话：**增删改都作用在"原料"（源页 + 词表 + 冲突裁决）上，卡片会据此重新长出来。** 这样才能保证可追溯。

## 增 / 删 / 改 速查

- **增**：放进 Confluence 或 `inbox/` → 重新生成 → 审批页确认主题 + 裁决冲突。
- **删**：从源头移除该页 / 在审批页 drop 该主题 → 重新生成。
- **改（事实值）**：改源页 → 重新生成；或冲突面板里选定正确值（冻结）。
- **改（主题/结构）**：审批页编辑词表 → 导出 → 重新生成。

## 技术附注（给跑流程的同事，非技术读者可跳过）

完整重建（含冲突复核）：

```bash
# 现有 md 语料
python -m backend.pipeline demo

# 现有语料 + inbox/ 里的新 JSON 页（新页才会和旧值冲突）
python -m backend.pipeline demo --config config.incoming.yaml
```

分步：`ingest → map → discover →（人工在 approve.html 冻结词表）→ reduce → review-conflicts → load`。

- `review-conflicts`：让大模型复核冲突并写 `outputs/conflicts.jsonl`；冲突裁决账本是 `outputs/conflict_decisions.jsonl`（**重建不删**，会自动重新套用）。
- 冲突相关接口：`GET /api/conflicts`、`POST /api/conflicts/resolve`。
- 收件箱、配置、自检细节见 `inbox/README.md` 与 `handoff/35`；接真实卡片见 `handoff/34`。
- ⚠ 别用 `pipeline demo` 子命令在生产"修数据"——它会清空 outputs 用合成 fixture 重建（除冲突账本外）。
