## 一、这次到底修了什么（大白话）

**修之前的毛病**：卡片被命中后去"回原文取证"时，如果这张卡登记的原文段落里**恰好没有答案**，系统就直接吐 `NO_ANSWER` 死在那儿。可同一个问题，**纯 RAG 反而能答上来**。也就是——**开了卡片，某些问题比不开还差**。这是个很糟的性质:你加了一层东西，结果把本来能答对的问题答砸了。

**修之后**：卡片**先全精度试答**;只有它答不出来(返回 NO_ANSWER)时，**才自动回退到 RAG 兜底**。所以:
- 卡片能答的时候 → RAG 一点不掺，答案确定、可追溯（卡片的价值完整保留）。
- 卡片答不出的时候 → RAG 接住，**绝不会比纯 RAG 更差**。

这就把"卡片在前、RAG 兜底"真正落地了。

## 二、为什么不是"把卡片和 RAG 混在一起"（我上一版说错了，已纠正）

我最初口误说"merge(卡片 refs + RAG 召回合并一起喂 LLM)"。**那是错的，已否决。** 原因:你的 Confluence 里有版本交叉混乱的页(v1 写 100、v2 写 200、某客户 case 写 50)。一旦把 RAG 召回混进来，那些过期/无关的数字又回到 LLM 面前，"对的文档、错的数字"问题原地复活——卡片**精确锁值**的价值就被你亲手稀释了。

正确做法是**分层**:卡片能答就纯卡片(锁死)，答不了才落 RAG(兜底)。**两段，不是一锅。**

## 三、记住卡片和 RAG 的定位(这是整件事的"意义")

- **RAG = 会查资料的实习生**:档案室里有的几乎都能翻到(召回广)，但每次翻的可能不一样、遇到多版本可能拿错、出事说不清出处。
- **卡片 = 盖了公章的标准答疑手册**:只收"必须有唯一正确答案"的那几条，每条写明值/出处/谁审的/何时审。翻到就是标准答案，能追责。

**卡片的价值不在"答对率"**(那是 RAG 的主场)，而在三件 RAG 结构上做不到的事:
1. **确定性 + 可审计**:答错了能查清"为什么错、找谁负责、怎么保证不再犯"。这就是"治理价值"。
2. **精确锁值**:多版本混乱时一锤定音，不让 LLM 在几个数字里瞎挑。
3. **枚举完整 + 矛盾检测**:整卡枚举不丢项;同名多值能报冲突。

**所以别给所有问题建卡**——那是用手工重建 RAG，纯亏(卡片真正贵在"维护":源文档一改就得跟着改)。卡片只占"答错代价大"的那一小撮。

## 四、这次**没有**解决什么(你要心里有数)

1. **如果某个 Golden 答不上的根因是"这张卡本该认领的那一节，建卡时漏登记了"**——那回退只是**止血**(RAG 替它救场)，**卡片本身还是残缺的**。你得回头补卡片抽取，否则这张卡永远靠 RAG 擦屁股，卡片那三个价值在这条问题上等于没有。**怎么发现**:见下面第五步的 Debug。
2. **`agentic-card-direct`(卡片直接拼字段值、不下钻)返回 NO_ANSWER 时不会回退**——这是另一条路径、另一类成因，本次没动。如果你要让 agentic 模式**彻底无死路**，那是单独一轮(见第六节可选项)。

## 五、你接下来要做的(按顺序)

1. **同步进内网 + 拉代码**:让 opencode `git pull` 取这次后端改动。前端那段(召回链路两段式渲染)我已写成 30 篇给 codex，让 codex 照着改。
2. **复测 Golden**(agentic 和 card-grounding 模式，**勾上 Debug**):重点看那些**以前 NO_ANSWER、现在能答**的问题。
3. **对每个"靠回退救回来"的问题,做一个判断**(这是关键动作):看 Debug 召回链路——
   - 它是不是走了回退?(`path` 以 `-then-rag-fallback` 结尾,或链路里同时有"失败的卡片下钻"+"RAG 救场")
   - 如果是,**看那张失败的卡 `missed`/覆盖不全的提示**:问自己——**这个问题该不该由这张卡答?**
     - **该**(属于卡片管的高价值名词)→ 这是卡片 source 建漏了,**记下来,去补这张卡的抽取**(让 opencode 在内网补 `source_section_ids`)。
     - **不该**(是个长尾/低价值问题,只是凑巧匹配上了卡)→ **不用管**,让 RAG 兜底就对了,这正是设计意图。
4. **做那个真正的战略决策:卡片层到底要多大。** 用我们聊过的四象限——**纵轴=答错代价(你/Business 判断)**、**横轴=RAG 现在答得行不行(测出来)**:
   - 代价高 → 建卡(哪怕 RAG 现在答得对,也建卡冻结,因为你不敢赌它换模型/改文档后还对)。
   - 代价低 → 一律不建卡,交给 RAG(答不好就忍,或优化 RAG 的 chunk/top_k)。
   - **频率只决定"先做哪张卡",代价决定"要不要做卡"。**
   - 让 Business 把核心问题往这四格里扔,你就知道卡片层该留哪些、砍哪些。

## 六、可选的后续(你决定要不要开)
- **(A) 把回退扩到 `agentic-card-direct`**:让 agentic 模式连"卡片直答字段值失败"也回退 RAG,彻底无死路。小改,要的话我开一轮。
- **(B) 卡片加权 + RAG 兜底的"软排序"**:如果你将来想让卡片"优先但不排他",可以做加权而非 merge。**但对'权威口径'类问题不推荐**(又会引入稀释)。除非有明确场景,否则别做。

## 七、你怎么验收这次改动
- 以前 NO_ANSWER 的 Golden,现在**要么卡片正经答了,要么 RAG 兜底答了**,**不该再有"卡片命中却死在 NO_ANSWER"**。
- 卡片本来就能答的问题,行为**没变**(没有被 RAG 污染,链路还是单段卡片取证)。
- Debug 链路能让你一眼看出"哪些问题是靠 RAG 救的、对应哪张卡覆盖不全"——这就是你筛"该补哪些卡"的工作台。

---
**一句话总结**:这次把"开卡片反而更差"的坑堵了(卡片答不了就让 RAG 接),同时**没有牺牲卡片在能答时的确定性**。真正需要你做的不是代码,是**第五步第4点那个决策——卡片层该多大、哪些名词值得建卡**。
